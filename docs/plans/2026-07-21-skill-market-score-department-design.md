# Skill 市场真实评分与部门发布设计

日期：2026-07-21
状态：已完成产品规则确认，待实施

## 背景

Skill 市场当前把 SkillHub 列表接口中的 `score` 直接显示为“综合评分”。该字段的实际用途是上游排序权重，取值可达到 `100000`，不是用户可读的评分。以 `ai-intelligence-investigator` 为例，当前镜像保存并展示 `100000.0`，而上游 TRACE 评估接口按五个维度计算出的综合评分为 `4.5/5`。

市场同时缺少部门发布能力。当前 SSO 回调经 `/api/provision/token` 只解析 `tokenName` 中的工号和姓名，没有接收、保存或授权使用部门信息。因此，仅在投稿表单添加部门选项不能形成可靠的访问控制。

## 目标

1. 将 SkillHub 排序权重与 TRACE 综合评分彻底分离。
2. 页面只展示真实的 `0–5` TRACE 评分；缺少评分时明确显示“待评分”或“未评分”。
3. 低速、可恢复地补齐全部 SkillHub 镜像的 TRACE 评分，不增加明显的服务器 IO 峰值。
4. 允许投稿者将 Skill 发布为“全公司”或“部门内”。
5. 普通用户只能发布到自己的 SSO 部门，管理员可选择任意已同步部门。
6. 在列表、搜索、详情、安装和下载等所有入口执行一致的部门访问控制。
7. 保持所有历史 SkillHub 镜像、企业 Skill 和社区投稿的现有可见性。

## 非目标

- 本次不引入员工手工维护部门。
- 本次不开发内部 Skill 的人工评分或点赞系统。
- 本次不使用 SkillHub 的排序权重推算 TRACE 评分。
- 本次不建设完整组织架构同步；部门目录由成功 SSO 登录获得的部门身份逐步登记。

## 已确认的产品规则

- 投稿时可选择“全公司”或“部门内”。
- 普通用户只能选择本人当前 SSO 部门。
- 管理员可以选择任意已同步部门。
- 部门 Skill 仅同部门用户和管理员可访问。
- 现有数据全部视为“全公司”。
- 推荐精选继续按上游推荐排序；按评分排序使用真实 TRACE 综合评分。

## 身份与部门模型

### SSO 身份契约

`/api/provision/token` 的成功响应在现有字段之外增加：

```json
{
  "status": "ready",
  "key": "...",
  "tokenName": "E000001-张三",
  "departmentId": "dept-123",
  "departmentName": "研发一部"
}
```

`departmentId` 是授权依据，必须稳定且不可由浏览器提供；`departmentName` 只用于展示。市场服务在 SSO 登录完成时校验并保存这两个字段。

为兼容 SSO 服务的滚动升级，部门字段暂时缺失时仍允许登录，但该用户只能使用全公司能力，不能访问或发布部门 Skill。响应中字段类型或配对关系非法时记录依赖错误，且不得从 `tokenName` 猜测部门。

这是一个跨服务契约变更：提供 `/api/provision/token` 的 provisioning 服务必须先支持新字段，市场服务才能获得真实部门。两端应按“先增加响应字段、再启用市场部门能力”的顺序发布；旧市场会忽略新字段，因此可以滚动升级。

### 数据模型

新增部门目录，至少包含：

- `department_id`：稳定主键。
- `display_name`：当前展示名称。
- `first_seen_at`、`last_seen_at`：首次和最近从 SSO 观察到的时间。

用户记录增加可空的 `department_id`，每次成功登录时更新。部门改名只更新目录显示名；员工调动后，下一次登录更新其部门关联。

发布范围使用明确枚举：

- `company`
- `department`

部门范围必须同时具有 `department_id`。投稿、审核读取模型和已发布社区 Skill 都暴露范围及部门展示信息。数据库迁移将所有历史记录填充为 `company`。

### 权限规则

- 普通用户创建或修订部门投稿时，服务端要求目标部门等于会话中的部门，不能相信表单提交的部门值。
- 管理员可以选择部门目录中的任意部门。
- 部门缺失的普通用户只能选择 `company`。
- 部门 Skill 的列表、搜索、详情、安装 Prompt、元数据和 ZIP 下载均执行同一授权规则。
- 无权访问时返回 `404`，避免通过 ID、总数或直接链接发现其他部门资源。
- 管理员可以访问所有部门 Skill。
- 审核员可处理审核队列中的部门投稿；发布后的市场浏览仍按本人部门授权，除非同时具有管理员角色。
- 用户调动后立即丧失原部门 Skill 的访问权，并获得新部门访问权。

## 评分模型

### 字段语义

SkillHub 镜像将评分数据拆分为：

- `rank_score`：上游列表排序权重。只用于复现推荐和同步顺序，不通过公共市场模型展示。
- `evaluation_score`：TRACE 五维综合评分，范围 `0–5`，可空。
- 五个 TRACE 维度分数：Trust、Reliability、Adaptability、Convention、Effectiveness，均可空。
- `evaluation_status`：`pending`、`running`、`completed` 或 `failed`。
- `evaluation_checked_at`、`evaluation_retry_at`、`evaluation_attempts` 和最近错误摘要。

旧 `score` 数据在迁移时保留为 `rank_score`，不得复制到 `evaluation_score`。

### TRACE 计算

评分任务请求上游 `/api/v1/skills/{slug}/evaluation`。五个维度均为必需项：每个维度先对其有效条目求平均，再对五个维度求平均，结果按页面需要显示一位小数和 `/5`。计算逻辑与 SkillHub 当前 TRACE 页面一致。

接口缺少必要维度、返回非法数值或请求失败时，不生成猜测评分；条目保持待评分或失败状态，并进入后续重试。

### 展示与排序

- SkillHub 卡片和详情页展示 `evaluationScore.toFixed(1) + "/5"`。
- 尚未获得 TRACE 结果的 SkillHub 条目显示“待评分”。
- 没有 TRACE 来源的企业或社区 Skill 显示“未评分”，不显示 `0`。
- “按评分排序”按 `evaluation_score` 降序，空值排在最后。
- “推荐精选”继续使用上游推荐或策展排序权重，不把它称为评分。
- 部署新模型后立即停止展示旧的 `100000.0`，无需等待评分补齐完成。

## 评分补齐任务

TRACE 补齐是独立于 SkillHub 内容镜像的持久化后台任务：

- 默认并发数为 2。
- 默认限制每分钟最多 60 个上游请求。
- 按数据库状态领取工作，不依赖仅存在于内存中的游标。
- 服务退出或重启后，超时的 `running` 项可重新领取。
- 单条失败不会停止整个队列。
- 失败使用有上限的指数退避并保留错误摘要。
- 首轮完成后，对超过 7 天的已评分条目低速重新评估。
- SkillHub 内容同步发现 Skill 已更新时，将其评分重新标记为待刷新。

按当前约 2.7 万条数据估算，首轮补齐约需 7–8 小时。限速值应通过配置调整，但默认值优先保护生产机器。

管理后台在现有 SkillHub 同步状态之外，单独展示 TRACE 任务的总数、待处理、运行中、已完成、失败、当前速率和最近错误，避免把内容同步与评分同步混为一个状态。

## 投稿与审核流程

投稿页增加发布范围控件：

- “全公司”始终可选。
- 有部门身份的普通用户可选择“我的部门（部门名称）”。
- 没有部门身份时禁用部门选项，并提示重新登录或联系 SSO 管理员。
- 管理员选择部门范围后，从已同步部门目录选择目标部门。

范围及部门属于受审核的投稿数据。审核页面必须展示当前目标范围；更新已发布 Skill 时，如范围发生变化，展示明确差异。范围变化不能绕过审核直接修改。

审计事件记录：

- 创建投稿时的范围与部门。
- 修订导致的范围变化。
- 审核和发布时采用的范围。
- 管理员代选部门的行为。

## 市场页面

普通用户提供三个入口：

- 全部可见
- 全公司
- 我的部门

管理员增加部门筛选器。Skill 卡片和详情页显示“全公司”或部门名称标签。服务端必须先应用可见范围，再执行搜索、分类、统计和分页，保证分页总数不泄露其他部门资源。

## API 与兼容性

- 公共 Skill 摘要和详情中的旧 `score: number` 改为可空的真实 TRACE 评分，并明确其 `0–5` 语义；内部调用同步升级。
- 如兼容成本更低，可在一次迁移期新增 `evaluationScore` 并停止读取旧 `score`，随后删除歧义字段。最终公共契约不得继续暴露排序权重为评分。
- Session/User 响应增加可选部门对象。
- 投稿创建、修订、摘要和详情增加发布范围与可选部门。
- 市场列表查询增加范围和管理员部门筛选参数。
- 所有新增字段对历史数据库有确定的默认迁移值。

变更公共 Protocol 或 Server `HttpApi` 后，从 `packages/client` 运行 `bun run generate`，不直接编辑生成目录。

## 错误处理

- TRACE 依赖不可用：保留旧的正确 TRACE 评分；无正确评分时显示待评分，并按退避策略重试。
- TRACE 返回结构异常：记录精简错误摘要，不保存部分或越界分数。
- SSO 缺少部门：登录继续成功，但仅启用全公司范围。
- 请求伪造部门：返回权限错误并写安全审计事件。
- 目标部门已不存在或未同步：管理员投稿请求失败，不接受自由文本部门。
- 部门资源越权：对市场读取和下载统一返回 `404`。

## 测试策略

### 评分

- 验证 `100000` 只进入 `rank_score`，不会进入公共评分。
- 使用真实形状的 TRACE fixture 验证五维和综合评分计算。
- 验证缺失维度、非法值、超时、重试、断点恢复和过期刷新。
- 验证评分排序、空值末尾、推荐排序不受影响。
- 验证 UI 显示 `4.5/5`、待评分和未评分。

### 部门

- 验证 SSO 部门写入、改名、员工调动和缺失部门兼容。
- 验证普通用户只能选择本人部门，管理员可选择任意已同步部门。
- 验证公司、同部门、异部门、审核员和管理员的列表、搜索、详情、安装与下载权限矩阵。
- 验证分页总数不会包含无权访问的部门数据。
- 验证历史数据迁移后保持全公司可见。
- 验证范围变更经过审核且写入审计日志。

## 发布与回滚

1. 先部署向后兼容的数据库迁移和服务端读取逻辑。
2. 升级 SSO provisioning 响应，确认新登录会写入部门。
3. 部署市场 UI 和部门投稿能力。
4. 启动限速 TRACE 补齐任务并观察 CPU、内存、磁盘 IO、请求错误率和队列进度。
5. 首轮完成后核对评分分布和代表性 Skill。

评分补齐任务可独立暂停，不影响 SkillHub 内容同步和市场访问。发生问题时可关闭部门投稿入口与 TRACE worker；历史数据仍保持全公司可见，旧排序权重仍可用于推荐顺序，但不得恢复为展示评分。

## 验收标准

- 市场任何位置不再显示 `100000.0` 作为综合评分。
- `ai-intelligence-investigator` 显示 `4.5/5`。
- TRACE 管理进度在服务重启后继续，不从头开始。
- 所有 SkillHub 条目最终进入已评分或可定位的失败状态。
- 普通用户可发布全公司或本人部门 Skill，不能伪造其他部门。
- 异部门用户无法通过列表、搜索、直链、安装或下载访问部门 Skill。
- 管理员可选择和管理任意已同步部门。
- 现有市场内容在升级后仍保持可访问。
