# SkillHub 全量预镜像设计

日期：2026-07-17

状态：已确认

目标代码线：`dev`

## 1. 背景

如影 Code Skill 市场当前通过 `SKILL_MARKET_SKILLHUB_LIMIT=30` 控制 SkillHub 同步规模。SkillHub 在 2026-07-16 返回约 78,000 条记录；移除限制后，现有同步器会一次并发请求约 782 个分页，并在任一请求失败时放弃整个 SkillHub 来源。当前线上因此只保留 18 个已验证 SkillHub 条目和 1 个其他来源条目。

现有 OSS 快照格式也不适合全量目录：每次发布都会重写并重新读取全部详情对象，而每个 API 请求又会从 OSS 加载整个快照及全部详情。目录扩大到数万条后，这会产生不可接受的 OSS 请求量、延迟和内存占用。

本设计将 SkillHub 全部可安装包预先下载、兼容修复、校验并镜像到 OSS，并将同步、发布和读取链路改造成可断点续传的规模化实现。

## 2. 已确认的产品决策

- 同步 SkillHub 可枚举的全部记录，不保留固定数量上限。
- 所有可处理的安装包在上架前预先镜像到 OSS，不采用安装时才回源下载。
- 采用 SQLite 持久化发现队列和镜像队列，服务器重启后自动续跑。
- 元数据问题进入宽松兼容流程；压缩包结构、资源限制、路径安全和明确恶意判定仍是不可绕过的安全边界。
- 缺失或非法 Skill 名称使用安全化后的 SkillHub `slug`，并规范化 `SKILL.md` frontmatter。
- SkillHub 文件清单与实际 ZIP 不一致时，以实际 ZIP 内容和计算出的哈希为准，同时保留兼容修复记录和风险说明。
- 每完成一批就逐步上架，不等待全部 78,000+ 条处理完成；现有目录在导入期间持续可用。
- 管理后台展示全量同步进度，并支持暂停、继续和重试失败项。
- 为提高吞吐，默认元数据并发为 8、安装包并发为 6；遇到 429、依赖延迟升高或本机资源压力时自动降低并发。

## 3. 目标与非目标

### 3.1 目标

- 最终镜像所有通过硬安全边界的 SkillHub 安装包。
- 单条记录或单个分页失败不能导致整个来源回退。
- 发现、下载、修复、上传和发布均可幂等重试并支持断点续传。
- 列表请求不读取全部详情对象，详情请求只读取目标 Skill 的详情。
- OSS 中相同内容只存储一次，目录版本切换保持原子性。
- 全量同步期间不阻塞社区投稿、审核和发布。
- 提供可观测的总数、进度、速率、上传量、重试和拒绝原因。

### 3.2 非目标

- 不关闭 ZIP 路径、压缩率、解压大小、文件数量和明确恶意报告校验。
- 不引入 Redis、Kafka 或新的集群基础设施。
- 不改变公开 Skill 市场 API 的请求与响应模型。
- 不保证上游缺失 `SKILL.md` 且没有可恢复说明内容的包可安装。
- 不在本次工作中实现多机并行 Worker；任务租约为后续横向扩展保留边界。

## 4. 总体架构

系统分为发现、镜像、目录构建和目录读取四个独立边界：

```text
SkillHub 分页 API
       │
       v
发现 Worker ──> SQLite 任务队列 ──> 镜像 Worker ──> 内容寻址包与详情（OSS）
                         │                  │
                         └────> 目录构建器 ─┴─> 版本化摘要索引 / 原子指针（OSS）
                                                   │
                                                   v
                                      API 摘要缓存 / 单详情按需读取
```

发现 Worker 只理解列表分页和上游记录版本；镜像 Worker 只处理一条 Skill 的详情、归档和 OSS 对象；目录构建器只从已镜像记录生成公开目录；HTTP 层只加载摘要索引并按需读取单个详情。任何边界都不需要把全量安装包或全量详情同时保存在内存中。

## 5. 持久化任务模型

新增一次数据库迁移，创建两个 STRICT 表：

- `skillhub_generations`：记录一次完整发现轮次的状态、上游总数、当前页、补扫次数、发现数、镜像数、拒绝数、上传字节数和时间戳。
- `skillhub_import_items`：以 SkillHub `slug` 为主键，记录上游版本、更新时间、任务状态、尝试次数、下次重试时间、租约、错误分类、原始包哈希、规范化包哈希、详情 JSON、修复记录和最近发现轮次。

任务状态为：

- `pending`：等待抓取或上游版本发生变化。
- `running`：已被 Worker 通过有期限租约领取。
- `mirrored`：规范化包、详情和图标已经写入 OSS。
- `retry_wait`：暂时性失败，等待下一次重试时间。
- `rejected`：触发不可绕过的安全边界，不能公开上架。

领取任务和写入结果使用短事务。Worker 崩溃后，过期的 `running` 租约自动回到可领取状态。相同 `slug + version + updated_at` 且已处于 `mirrored` 的记录不重新下载。

## 6. 全量发现与补扫

发现流程先读取第一页获得 `total`，然后以每页 100 条、默认并发 4 的方式分批读取剩余页面。每个成功页面独立写入 SQLite，分页失败在重试完成前不会把来源标记为完整。

SkillHub 使用按评分排序的页码分页，扫描期间排名变化可能造成跨页移动。因此首轮完成后必须再次从第一页补扫。连续一轮没有发现新 `slug`，且已读取数量与当轮上游总数一致时，发现轮次才算完成；最多连续补扫三轮，仍不稳定时保留 `stale` 状态并在下一轮继续，不能错误地下架未看到的旧条目。

只有完整发现轮次结束后，才能把连续两轮未出现的旧记录标为下架。临时分页失败不能删除目录条目。

## 7. 镜像与兼容修复

### 7.1 获取流程

镜像 Worker 为每条任务获取详情、文件清单、版本历史和 ZIP。元数据请求默认并发 8，安装包处理默认并发 6。每个响应继续执行 HTTPS 主机白名单、重定向边界、响应大小和 Schema 校验。

网络超时、HTTP 429、HTTP 5xx 和 OSS 临时错误为可重试错误。单次处理遵守 `Retry-After`，否则执行带抖动的指数退避；跨轮次重试没有固定次数上限，但退避最大为 24 小时。

### 7.2 宽松兼容

ZIP 存在根 `SKILL.md`，但 frontmatter 的 `name` 缺失或不安全时，使用安全化后的 SkillHub `slug` 重写 `name`。`description` 缺失时使用 SkillHub 详情摘要。规范化过程只修改必要的 frontmatter，保留正文和其余文件内容。

上游文件清单数量、路径或哈希与 ZIP 实际内容不一致时，不信任上游清单；系统从安全解压后的实际内容重新生成文件清单。规范化后的 ZIP 重新计算 SHA-256，详情记录原始来源、修复类型和新的实际清单。

如果根 `SKILL.md` 缺失，但归档中存在唯一且安全的嵌套 `SKILL.md`，将该 Skill 目录提升为归档根后继续规范化。没有唯一可恢复 Skill 内容的包进入 `rejected`，因为它无法形成可执行的 Skill。

### 7.3 硬安全边界

以下情况必须拒绝，不受宽松模式影响：

- ZIP 路径穿越、绝对路径、符号链接逃逸或重复冲突路径。
- 压缩包超过 50 MiB、解压后超过 100 MiB 或文件数超过 1,000。
- 内容无法完整读取或无法计算实际哈希。
- 外部安全报告明确给出恶意结论。
- 规范化后仍无法产生安全且唯一的 Skill ID。

未知和警告风险允许镜像，但详情必须保留风险原因。明确恶意条目不上传公开包，也不进入目录。

## 8. OSS 布局与原子发布

包和详情改为内容寻址，避免每个目录版本复制全部对象：

```text
skill-market/
  current.json
  indexes/<revision>/catalog.json
  indexes/<revision>/facets.json
  details/<detail-sha256>.json
  packages/<package-sha256>.zip
  icons/<icon-sha256>.<ext>
```

`catalog.json` 保存公开摘要以及每条摘要对应的详情对象键。旧目录格式继续可读，新格式发布后不再为每个 revision 重写全部详情。目录构建器只上传新产生或内容发生变化的详情、包和图标，再写入新的摘要索引与 facets，最后更新 `current.json`。

发布前校验新的索引、facets、变更详情和引用对象；不再对每次发布的全部 78,000 个详情执行 PUT、HEAD 和 GET。`current.json` 仍是唯一原子切换点，失败发布不会影响上一版本。

每新增 2,000 个已镜像条目或距离上次发布满 30 分钟时构建新目录。全量发现和镜像结束后强制发布最终版本。导入期间 SkillHub 来源状态为 `stale`，连续补扫完成且所有任务均为 `mirrored` 或 `rejected` 后改为 `fresh`。

## 9. API 读取模型

公开 HTTP API 路由和响应 Schema 保持不变。

服务端将 `current.json`、`catalog.json` 和 `facets.json` 缓存在进程内，并以 revision 与 60 秒 TTL 刷新。列表、搜索、排序和 facets 只访问内存中的摘要，不加载详情对象。详情、版本和下载接口根据摘要中的详情对象键读取单个内容寻址对象，并使用小型 LRU 缓存降低热门详情的 OSS 请求量。

旧格式加载器保留到迁移完成，部署后先读取当前 19 条快照并写入新任务表与内容寻址对象。迁移完成前 HTTP 层可继续读取旧快照；新 `current.json` 发布后自动切换到新格式。

## 10. 管理与可观测性

管理后台增加 SkillHub 同步进度区，展示：

- 上游总数、已发现、待处理、处理中、已镜像、等待重试和硬拒绝数量。
- 已上传字节数、最近一分钟处理速率、预计剩余时间和最近成功发布时间。
- 当前发现页、补扫轮次、有效并发数和最近的分类错误。

管理员可以暂停、继续和重新尝试 `retry_wait` 或选定的 `rejected` 任务。暂停只停止领取新任务，不中断正在安全写入 OSS 的单条任务。所有管理操作写入现有审计事件表。

结构化日志和指标记录阶段、耗时、错误分类、HTTP 状态和计数，但不记录 OSS 密钥、Cookie、完整安装包内容或用户会话。

## 11. 性能与限流

默认并发为元数据 8、安装包 6、分页 4。控制器按以下规则自动调整：

- 收到 429 或连续依赖超时时立即将相关并发减半，最低为 1。
- 连续五分钟无 429 且 p95 延迟稳定时，每分钟增加 1，最高不超过默认值。
- 进程内存超过配置软阈值时暂停领取新包，低于恢复阈值后继续。
- 单个 Worker 任意时刻最多持有 6 个、每个不超过 50 MiB 的压缩包。

同步 Worker 与社区发布使用现有目录发布租约协调。长时间下载和处理不持有目录发布租约，仅在生成并切换目录版本时短暂持有，避免阻塞投稿发布。

## 12. 测试策略

单元测试覆盖：

- 78,000 条分页只产生受控并发，分页失败可独立重试。
- 任务领取、租约过期、断点续传、幂等完成和版本变化重新入队。
- 非法或缺失名称修复、唯一嵌套 Skill 提升和实际清单重建。
- 路径穿越、归档超限、内容读取失败和明确恶意报告仍被拒绝。
- `Retry-After`、指数退避和自适应并发升降。
- 内容寻址对象去重、旧新快照兼容和原子指针切换。

集成测试模拟 HTTP 429、HTTP 5xx、OSS 上传失败、Worker 进程中断、重复任务和重复包哈希。恢复后必须得到相同目录，且没有重复公开对象或丢失已完成任务。

规模测试使用 80,000 条合成摘要，验证列表请求只读取指针和摘要索引，详情请求只读取单个详情对象；目录发布只写入变更对象，不能随目录总量产生等量详情 PUT/GET。

## 13. 上线与回滚

上线顺序：

1. 备份并校验 SQLite，运行新增迁移。
2. 部署兼容旧快照的新 API、队列、Worker 和管理进度界面。
3. 导入当前 19 条并发布新格式目录，执行列表、详情、下载和投稿发布冒烟测试。
4. 先领取 100 条 SkillHub 任务进行生产冒烟，检查成功率、OSS 对象、内存、限流和抽样安装。
5. 冒烟通过后移除 `SKILL_MARKET_SKILLHUB_LIMIT`，启动全量发现和镜像。
6. 连续补扫无新增、所有任务收敛并完成抽样安装后，将来源状态切换为 `fresh`。

任何阶段失败时暂停 Worker，不再领取新任务，并将 `current.json` 指回上一个已验证 revision。内容寻址对象是不可变且未被指针引用时不可见，因此不需要在紧急回滚中删除；后续维护任务可清理长期无引用对象。

## 14. 验收标准

- SkillHub 固定 30 条限制已移除，发现总数与稳定补扫后的上游可枚举总数一致。
- 所有任务最终处于 `mirrored` 或带明确硬安全原因的 `rejected`。
- 管理后台能显示实时进度、速率、上传容量和预计剩余时间，并能暂停、继续和重试。
- 服务器重启、上游 429 和 OSS 临时失败后能从持久进度继续，不重做已镜像且版本未变化的条目。
- API 列表、详情、版本和下载响应保持兼容，现有 Web 与桌面端无需修改调用方式。
- 80,000 条规模下，列表请求不发起逐详情 OSS 请求，详情请求最多读取一个未缓存详情对象。
- 抽样安装的包哈希与目录声明一致，规范化包可以被如影 Code 正常安装。
- 全量完成后 SkillHub 来源状态为 `fresh`，现有社区和企业条目仍完整可用。
